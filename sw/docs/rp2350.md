# RP2350 support (Raspberry Pi Pico 2 / Pico 2 W, PicoGUS v2.1 THT)

The PicoGUS firmware builds for the RP2350 as well as the RP2040, from the
same source. The RP2040 firmware is unaffected by the port: apart from the new
checks when flashing firmware and the new chip type register, the RP2040
images are the same as before.

**Status: builds and passes static checks, not yet tested on hardware.** See
the [hardware test checklist](#hardware-test-checklist).

## Supported hardware

| Board | Chip | Firmware | NE2000/WiFi firmware |
|---|---|---|---|
| PicoGUS 1.x / Femto with a Raspberry Pi Pico (W) | RP2040 | `picogus.uf2` | `pg-ne2k.uf2` (Pico W) |
| PicoGUS 2.0 (chip-down) | RP2040 | `picogus.uf2` | – |
| PicoGUS 1.x / Femto with a Raspberry Pi Pico 2 (W) | RP2350A | `pgus2350.uf2` | `ne2k2350.uf2` (Pico 2 W) |
| PicoGUS v2.1 THT (Waveshare Core2350B2) | RP2350B | `pgus-v21.uf2` | – |

Pico-footprint modules like the Pico 2 have the 30-GPIO RP2350A. Of the
48-GPIO RP2350B boards only PicoGUS v2.1 is supported (see
[PicoGUS v2.1 THT](#picogus-v21-tht-core2350b2-rp2350b)): board detection
reads GPIO29 through the ADC, and the RP2350B ADC inputs are GPIO40–47, so
other RP2350B boards (such as the Pimoroni Pico Plus 2) stop the build with
an error.

The RP2040 and RP2350 firmwares are not interchangeable, and three things
keep them apart:

- the USB bootloaders only accept UF2 files for their own chip;
- `pgusinit /flash` asks the card which chip it has (firmware from before
  RP2350 support doesn't answer, which means RP2040) and refuses a file for
  the other one before anything is sent to the card;
- the firmware checks every UF2 block it is sent and refuses a file for the
  other chip before erasing anything.

The Pico 2 and v2.1 firmware files are both RP2350 files, which none of
these checks can tell apart: use `pgus-v21.uf2` on v2.1 and `pgus2350.uf2`
on a Pico 2. pgusinit names the right file for the card when it refuses one.

## Building

Needs pico-sdk 2.3.1, pico-extras `sdk-2.3.1` and arm-none-eabi-gcc, with
`PICO_SDK_PATH` and `PICO_EXTRAS_PATH` set. SDK 2.3 or later is required for
RP2350: the multifw link scripts and the board files rely on it.

The release files for every platform:

```sh
sw/scripts/build_release.sh                  # binaries/: picogus.uf2 pg-ne2k.uf2 pgus2350.uf2 ne2k2350.uf2 pgus-v21.uf2 (+ DOS tools)
sw/scripts/build_release.sh --experimental   # also binaries/experimental/, see sw/experimental/README.md
```

Any mix of firmware variants:

```sh
sw/scripts/build_variants.sh                  # multifw + ne2k for rp2040, rp2350 and picogus21
sw/scripts/build_variants.sh -p rp2350 all    # every variant, Pico 2 only
sw/scripts/build_variants.sh --list           # variants, their PROJECT_TYPEs and file names
```

UF2 files are collected in `binaries/`, and each build gets its own directory
under `build/<platform>/<variant>`. The RP2350 release files have names of
their own that survive a DOS (8.3) file system; other variants get an
`-rp2350` or `-v21` suffix. CI runs the same scripts.

A single build works as before, with `-DPICO_PLATFORM=rp2350` added:

```sh
cmake -S sw -B build-rp2350 -DPICO_PLATFORM=rp2350 -DPROJECT_TYPE=MULTIFW
cmake --build build-rp2350
```

The board then defaults to `pico2_fast` (`pico2w_fast` for NE2K). Passing an
RP2350 board with `-DPICO_BOARD` also works, and `-DPICO_BOARD=picogus21`
builds for v2.1. RISC-V (`rp2350-riscv`) is not
supported, as the OPL emulator and the multifw bootloader contain Arm code.

## What is different on RP2350

Chip differences are kept in a few places: `system/platform.h` (small helpers
that compile to the original code on RP2040), the board headers in `boards/`,
and chip-specific blocks in `CMakeLists.txt`, `system/overclock.h`,
`system/pico_reflash.c`, `multifw/` and `resampler/resampler.hpp`.

**GPIO.** RP2350 pads come out of reset with the input buffer disabled and the
pad isolation latch set. `gpio_set_function()` clears both, but the ISA bus
pins that are only ever sampled by PIO (AD0–AD9, IOR, IOW, DACK, TC) never go
through it and would read as 0. They are enabled explicitly
(`platform_gpio_enable_input()`), the same way the ISA analyzer firmware does
it.

**Overclock** (`system/overclock.h`). Still 370 MHz, with the core voltage at
1.30 V (1.25 V on RP2040): the RP2350 is rated for 150 MHz at 1.10 V, and
1.30 V is the highest setting that doesn't need `vreg_disable_voltage_limit()`.
Override with `PICOGUS_VREG_VOLTAGE`.

**Flash clock.** On RP2040, boot2 sets the flash clock divider
(`PICO_FLASH_SPI_CLKDIV 4` in the board header) at startup and again after
every flash erase or program. The RP2350 has no boot2 in front of the image,
and its bootrom leaves the flash interface (QMI) at a divider that suits
150 MHz. The RP2350 builds therefore embed the SDK's XIP setup function
(`PICO_EMBED_XIP_SETUP=1`), which does what boot2 does on RP2040: it applies
`PICO_FLASH_SPI_CLKDIV 6` (61.7 MHz at 370 MHz) and `PICO_FLASH_SPI_RXDELAY 4`
from the board header at startup, and the SDK runs it again after every flash
erase and program. This matters because, since v4.2.0, settings are saved and
firmware is flashed without leaving 370 MHz.

**Multifw.** RP2350 images have no 256-byte boot2 in front of the vector
table, so the bootloader jumps to the start of the firmware slot (and sets
VTOR through `M33_VTOR_OFFSET`). The firmwares are linked with
`multifw/rp2350/fw_memmap_c2ram.ld`, which is the SDK's copy-to-RAM script
with the flash region replaced by the firmware's slot, and `uf2create` writes
the RP2350 Arm-Secure UF2 family ID. Each image's runtime init resets the
bootrom's state, so starting a second image after the bootloader works as on
RP2040.

**UF2 files and erratum RP2350-E10.** The RP2350 board headers turn
`PICO_RP2350_A2_SUPPORTED` off for cmake, so picotool doesn't add the E10
workaround block to UF2s. E10 is about dragging a UF2 onto a board whose flash
has a partition table, which PicoGUS doesn't use, while the workaround block
targets the last flash sector (where PicoGUS keeps its settings) and is a
separate "file" inside the UF2 that `pgusinit /flash` can't handle. The C code
keeps its A2 workarounds.

**Reboot after `pgusinit /flash`** uses the watchdog on RP2350, as a mode
switch does; Arm `SYSRESETREQ` only restarts the processors there.

**Resampler.** The OPL resampler's Cortex-M0+ inline assembly can't be
register-allocated for Cortex-M33, so RP2350 uses an equivalent C loop (same
wrapping 32-bit arithmetic).

**NE2000.** The CYW43 SPI clock divider is 4 on RP2350 (46.25 MHz, within the
CYW43439's 50 MHz limit); RP2040 keeps its divider of 3 (61.7 MHz).

**Settings** are still kept in the last flash sector, which is at 4 MB − 4 KB
on the Pico 2's 4 MB flash (16 MB − 4 KB on v2.1).

**Identification.** RP2350 builds append ` (RP2350)` to the firmware version
(` (RP2350B)` on v2.1), and the new control register `CMD_CHIPTYPE` (F1h)
reports the chip to pgusinit, which shows it on its hardware line.

### Errata reviewed

- RP2350-E1 (interpolator shifts are rotates): every interpolator lane used
  masks off the rotated-in bits (emu8950 slot renderer, SB linear
  interpolation, clamp), so results match RP2040.
- RP2350-E2 (SIO spinlock aliasing): the SDK uses software spinlocks on
  RP2350; PicoGUS code only uses the SDK spinlock API.
- RP2350-E9 (A2 only, input pad leakage): bus inputs are driven by the
  board's transceivers; DACK and TC keep the same pull-downs as on RP2040.
- RP2350-E12 (USB status synchronisation): needs clk_sys ≥ 1.1 × clk_usb,
  which holds at 370 MHz.
- RP2350-E27 (bus priority wiring): PicoGUS doesn't change bus priorities.

### Earlier RP2350 work upstream

The `rp2350` and `rp2350-wip` branches of polpo/picogus (2024–2025, based on
firmware 2.x/3.x) were the first experiments on this chip. What they found is
covered here: the PIO input pins need enabling, the alarm pool's timer IRQ is
looked up instead of being hard-coded (already in the mainline), and the reset
reason comes from POWMAN. They ran at 366 MHz and 1.25 V on a Pico 2. Two
things from those branches are not in this port:

- they turned MPU-401 off in GUS mode ("not working on rp2350 for some
  reason"). The MPU-401 emulation has been reworked since, so it is left on;
  it is on the test checklist;
- `PSRAM_XIP`, GUS RAM in a QMI PSRAM chip on the second chip select, for
  boards that have one, through a branch of the rp2040-psram library. The
  Pico 2 has none: there GUS RAM stays on the PicoGUS board's SPI PSRAM,
  driven by PIO as on RP2040. PicoGUS v2.1 does have one and uses it through
  `system/psram_qmi.[ch]`, see below.

## PicoGUS v2.1 THT (Core2350B2, RP2350B)

The through-hole v2.1 board (on the `hw2.1-tht` branch) is the PicoGUS 2.0
circuit on a Waveshare Core2350B2 module: RP2350B, 16 MB flash, 12 MHz
crystal and 8 MB PSRAM on the RP2350B's QMI (chip select CS1 = GPIO47). Build
it with `-DPICO_BOARD=picogus21` (`boards/picogus21.h`), or
`sw/scripts/build_variants.sh -p picogus21`. The NE2000 firmware needs a
Pico W and is not built for it.

* **Board type.** `PICOGUS_BOARD_V21` sets the board type to PicoGUS 2.0 at
  compile time instead of reading GPIO29 with the ADC; the LED (GPIO23), the
  M62429 Waveblaster volume (GPIO24/25) and every ISA/I2S pin are v2.0's.
* **GUS sample RAM in the module's PSRAM** (`PSRAM_QMI`,
  `system/psram_qmi.[ch]`). The GUS firmware's PSRAM calls (`psram_read8`,
  `psram_write32_async`, ...) become plain memory accesses to QMI window 1
  (uncached alias 0x15000000; the firmware keeps the XIP cache off). At boot
  the PSRAM is identified (AP Memory KGD 0x5D; a Core2350B0 without PSRAM
  reports none), reset and switched to QPI; window 1 is set up for quad reads
  (0xEB, 6 wait cycles) and writes (0x38), with the clock divider from clk_sys
  (370 MHz / 4 = 92.5 MHz) and the read sample delay calibrated against a
  test pattern. The SDK's flash functions leave window 1 without its write
  format, so the setup is registered with them
  (`flash_set_qmi_cs1_setup_function()`) and runs again after every flash
  erase and program. While a settings save writes the flash, GUS core 1 is
  held (multicore lockout, no timeout), as it plays from the PSRAM. The
  existing PSRAM self-test runs on it. v2.0's APS6404L on GPIO0–3 (PIO SPI)
  is not on the board; GPIO0–3 are free.

## Hardware test checklist

None of this has run on an RP2350 yet. Things to check on a PicoGUS 1.x board
with a Pico 2 (and a Pico 2 W for NE2000):

1. Boot from a drag-and-drop `pgus2350.uf2`; pgusinit detects the card, shows
   `(RP2350)` in the firmware version and `RP2350 (Pico 2)` on its hardware
   line.
2. Every mode, and switching between them with `/mode` (exercises the multifw
   bootloader jump and watchdog reboot).
3. GUS mode: PSRAM detection (the firmware tries both SPI timing strategies),
   long demos with DMA, and MIDI output from a game using GUS and MPU-401.
4. SB mode: 8/16-bit, auto-init and high-speed DMA, OPL3, CD-ROM images from
   USB, CD audio, joystick, MPU-401 MIDI out.
5. AdLib, MPU, PSG (Tandy/CMS) and USB modes, including the USB mouse.
6. `pgusinit /save` followed by more use without a reboot (flash write at
   370 MHz, then flash reads through the re-applied clock divider: AdLib mode
   reads its tables from flash), then a reboot and a power cycle.
7. `pgusinit /flash` with `pgus2350.uf2`, with `picogus.uf2` (must be refused
   by pgusinit; with an older pgusinit, by the firmware, without harming the
   card), and with a truncated file.
8. NE2000 on a Pico 2 W: connect, `/wifistatus`, file transfers.
9. Long runs at 370 MHz / 1.30 V, ideally in a warm case. If flash reads
   misbehave, raise `PICO_FLASH_SPI_CLKDIV` or adjust `PICO_FLASH_SPI_RXDELAY`
   in `boards/pico2_fast.h`; if the core is unstable, the voltage and
   `RP2_CLOCK_SPEED` are the knobs.

On PicoGUS v2.1 (Core2350B2), with `pgus-v21.uf2`, additionally:

10. pgusinit shows `Hardware: PicoGUS v2.1 THT (RP2350B)`.
11. GUS mode on the module PSRAM: the boot log (`-d` debug build) shows the
    PSRAM ID, size and the calibrated read delay; GUS demos with large patch
    sets (GUS memory full), DMA uploads, and a settings save while GUS is
    playing (flash write with core 1 held, then the PSRAM window set up again).
12. If PSRAM reads misbehave at 370 MHz, lower `PICOGUS_PSRAM_MAX_SCK_HZ`
    (default 109 MHz, giving 92.5 MHz).
